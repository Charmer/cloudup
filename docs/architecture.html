cloudup · архитектура

Cloudup изнутри

Локальный Go-сервер, который раскладывает один файл сразу по нескольким облачным хранилищам — и ведёт журнал, достаточно честный, чтобы через месяцы ответить, лежит ли файл на месте и не изменился ли он.

Ориентация

Общая форма

Cloudup — это один Go-процесс. Он слушает 127.0.0.1:3000, отдаёт REST API под /api/v1 и на том же порту раздаёт собранный Vue-фронтенд прямо с диска. Ни второго процесса, ни отдельного сервера для фронтенда, ни обратного прокси в обычном случае.

Почти весь дизайн объясняется тремя идеями:

  • Ядро не знает ни об одном конкретном хранилище. Провайдер — это пакет, который регистрирует себя сам; очередь, история и API видят только интерфейс.
  • Прогресс тянут, а не пушат. Клиент опрашивает снепшот. Ни WebSocket, ни SSE, ни договорённостей о протоколе — а это важно, потому что клиентом вполне может быть чужой код.
  • Каждая загрузка оставляет проверяемый след. Чек-сумма ложится в локальный SQLite, и позже тот же провайдер, который её посчитал, может ответить, совпадает ли файл на хранилище.

Запуск

Один бинарник, два режима

Один и тот же исполняемый файл — и десктопное приложение, и безголовый сервис. Чем он станет, решается при старте флагом -gui, и когда флаг не передан, режим определяется, а не берётся по умолчанию: на Linux по $DISPLAY/$WAYLAND_DISPLAY, на Windows по $SESSIONNAME (эвристика слабее — для настоящей службы флаг лучше передать явно), на остальных платформах предполагается десктоп.

В GUI-режиме есть иконка в трее, браузер открывается сам, а лог уходит в файл — консоли обычно всё равно не видно. В headless-режиме это обычный процесс на переднем плане с логом в stdout: та форма, которая нужна под systemd, в контейнере или рядом с другим backend-приложением.

API-токен генерируется заново при каждом старте (если его не фиксирует CLOUDUP_API_TOKEN) и никогда не пишется на диск. Когда фронтенд раздаётся локально, токен инжектируется прямо в index.html — открывшийся браузер уже авторизован, и в лог ничего не попадает. И только в API-only режиме (-static "") токен доходит до лога, потому что взять его больше негде.

Почему CORS выключен по умолчанию

При обычном запуске на одном порту страница и API имеют один origin, поэтому браузер вообще не начинает CORS-проверку — а не-браузерный клиент эти заголовки не читает никогда. CORS нужен ровно в одной ситуации: фронтенд отдан с другого origin, например dev-сервером Vite. Отсюда флаг -cors-origin, пустой по умолчанию, который просто не вставляет middleware в цепочку.

И стоит быть точным в том, чем CORS не является: он никогда не защищал этот API. Чужая страница и без него может отправить запрос на loopback-порт — same-origin policy запрещает только прочитать ответ. Защищает bearer-токен.

Главный механизм

Путь загрузки

Файл приходит обычным multipart/form-data. Прежде чем что-то попадёт в очередь, тело запроса сбрасывается в spool-файл на локальный диск — и этот крюк несёт на себе больше всего смысла во всём конвейере.

Одно следствие стоит принять сразу: HTTP-обработчик отвечает 202 с идентификатором задачи почти мгновенно. В этот момент он ничего не загрузил — он лишь припарковал байты и поставил работу в очередь. Всё дальнейшее наблюдается поллингом /api/v1/tasks.

Снепшот, который опрашивает клиент, поддерживает единственный фоновый читатель канала событий очереди. У этого канала может быть только один потребитель — поэтому даже горутина, убирающая spool-файлы, опрашивает тот же снепшот, а не читает канал вторично.

Второй вход в ту же очередь

Слежение за папками

internal/watch — второй способ положить задачу в queue.Manager, минуя HTTP и spool-файл целиком: fsnotify следит за локальной папкой/файлом на той же машине, где работает сам cmd/server, и по устоявшемуся (тихий период 2 с без новых событий) изменению сразу вызывает Enqueue с Open(), читающим локальный файл напрямую — spool не нужен, потому что файл на диске и так можно переоткрыть на любой повтор попытки, в отличие от тела HTTP-запроса.

Только локальная файловая система cmd/server

REST — протокол, которым другие программы говорят с cloudup; сам процесс — обычный Go-бинарник с полным доступом к своей ФС (так же он уже читает frontend/dist/config.json с диска). Следить за папкой на машине стороннего клиента (например, сервера, встраивающего cloudup) физически невозможно — та сторона следит сама и зовёт обычный POST /uploads.

Планирование

Очередь: полосы и retry

У каждого подключения своя полоса. Полосы идут одновременно; внутри полосы файлы стартуют в том порядке, в котором были поставлены. Настройка параллельности поднимает, сколько самых старых ожидающих файлов полосы могут идти одновременно — но порядок она не меняет.

Ошибки повторяются с экспоненциальной задержкой. Задача, отменённая на лету, записывается как отменённая, а не уходит обратно в retry-цикл. Большие файлы автоматически переключаются на порционный путь провайдера при превышении порога 64 МиБ — и это число намеренно ниже лимита Dropbox в 150 МБ на один запрос, потому что для этого провайдера порционная загрузка и есть то, что вообще делает большие файлы возможными.

Хранилища

Провайдеры и чек-суммы

Каждый провайдер реализует один маленький обязательный интерфейс. Всё, что умеют не все хранилища — порционная загрузка, проверка чек-суммы, проверка существования, описание собственной формы конфига — это отдельные опциональные интерфейсы, которые ядро обнаруживает через type assertion. Добавить хранилище значит написать пакет и один анонимный импорт; в ядре не меняется ничего.

Самое интересное расхождение — как проверяется целостность, потому что это решение целиком отдано провайдеру:

WebDAV, S3, Dropbox, FTP и SFTP не отдают надёжный хэш содержимого, поэтому считают его сами во время загрузки и проверяют, скачивая файл обратно. Google Drive, Backblaze B2, Yandex.Disk и OneDrive надёжный хэш публикуют, и для них проверка — это запрос метаданных. Именно поэтому B2 сделан на своём нативном API, а не через S3-совместимый слой, который тоже бы работал.

Для ядра эта разница невидима: все девять удовлетворяют одному интерфейсу, а метка алгоритма хранится в журнале как непрозрачное значение и позже возвращается тому же провайдеру. Для случая «своя чек-сумма» метка вынесена в общую константу, а не продублирована в каждом пакете — она персистится, и опечатка в четвёртой копии молча наплодила бы записи истории, которые невозможно проверить.

Одна тонкость про порционную загрузку: чек-сумма обязана получиться одинаковой, ушёл файл одним запросом или двадцатью. Это выполняется потому, что поток оборачивается для хэширования один раз, до нарезки — хэш покрывает весь файл и ничего не знает о том, как его порезали для передачи.

Учётные данные

Секреты и OAuth

Два хранилища, разделённые намеренно. JSON-конфиг держит только несекретные метаданные подключения — имя, тип, endpoint, бакет. Всё секретное уходит в системное хранилище ключей ОС (Windows Credential Manager, macOS Keychain, Secret Service на Linux) с привязкой к подключению. В файле конфига пароля не бывает никогда, а интерфейс, который видят провайдеры, доступен только для чтения — так что попытка провайдера записать секрет просто не скомпилируется.

Google Drive, Dropbox, Yandex.Disk и OneDrive требуют интерактивного шага согласия, прежде чем подключение вообще заработает, и в статическую форму это не укладывается. Такой флоу зарегистрирован на тип провайдера, а не захардкожен, и поэтому API отдаёт его обобщённо: клиент спрашивает, каким типам нужен OAuth, один раз задаёт для этого типа общие для приложения client credentials, а затем авторизует каждое подключение. Редирект после согласия ведёт не на отдельный временный процесс, а на GET /api/v1/oauth/callback того же REST API сервера — построенный из того же адреса, по которому браузер и так уже обращается к API, поэтому работает одинаково и для локального запуска, и для удалённого сервера за reverse proxy.

Общие для приложения client id и secret лежат в хранилище ключей под псевдо-идентификатором подключения — так они разделяются всеми подключениями этого типа и по-прежнему не попадают в файл конфига.

Долговечность

Журнал загрузок

Каждая завершённая попытка попадает в локальную таблицу SQLite: локальный путь и размер, подключение, путь на хранилище, чек-сумма и метка алгоритма, время и результат. Это намеренно отделено от лога приложения — здесь бизнес-данные, а не диагностика.

Смысл журнала — в перепроверке. Попросите проверить запись, и он резолвит провайдера и сообщает одно из пяти состояний:

  • ok — на месте, содержимое совпадает.
  • missing — файл удалили или переименовали на хранилище.
  • mismatch — файл есть, но содержимое изменилось.
  • unverifiable — этот провайдер проверить не может; нейтральный ответ, не ошибка.
  • error — до хранилища не удалось дойти.

Проверку можно включить автоматически после каждой успешной загрузки. По умолчанию она выключена, и не случайно: для пяти провайдеров, считающих хэш сами, это означает повторное скачивание каждого загруженного файла, то есть удвоение трафика. Когда включена, она идёт в отдельной горутине и не держит слот полосы.

Локализация

Языки

Переводы отдаёт бэкенд, а не сборка фронтенда. Английский и русский вшиты в бинарник; чтобы добавить язык или переопределить отдельные ключи встроенного, достаточно положить JSON-файл в папку languages/ рядом с исполняемым файлом — без пересборки ни одной из половин.

Две детали делают это приятным в использовании. Зарезервированный ключ __name__ хранит самоназвание языка, поэтому новый язык подписывает себя в переключателе без единой правки кода. А недостающие ключи дополняются английскими при загрузке каталога, так что неполный перевод всегда безопасен и клиенту не нужна своя логика fallback.

Почему это живёт на сервере, а не во фронтенде: фронтенд заменяем по замыслу, поэтому каталоги принадлежат API. К тому же браузер не умеет листать директорию — сервер умеет.

Честный учёт

Шероховатости

То, что следующей сессии лучше знать, чем обнаруживать заново:

  • У файловых операций Google Drive нет интеграционных тестов. Качественного in-memory фейка под wire-протокол Drive v3 не нашлось, а самодельный рискует дать ложную уверенность. Перед тем как доверять — проверка на живом аккаунте.
  • У B2 пока нет порционной загрузки. Свой large-file API у него есть; очередь начнёт им пользоваться в тот момент, когда провайдер реализует интерфейс.
  • Прокси не реализован, как и ограничение скорости загрузки и сохранение структуры папок при загрузке нескольких файлов.
  • Три вещи требуют человека. Клик по иконке в трее, автоопределение headless на реальном сервере без дисплея и то, как фронтенд на самом деле рисуется — ничего из этого не проверить из консоли разработчика.

С другой стороны, весь набор тестов проходит многократно, а не однажды — именно это делает видимой утечку состояния между прогонами; а у HTTP-слоя теперь есть тест, который падает, если какой-нибудь маршрут перестанет регистрироваться. Ровно этот класс ошибки однажды позволил уехать в релиз целому OAuth-флоу провайдера, подключённому в никуда.

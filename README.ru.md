# Cloud Uploader

*[Read in English](README.md)*

Локальный REST API-сервер (Go) + браузерный фронтенд (Vue 3, в
[`frontend/`](frontend)) для **параллельной** загрузки файлов в несколько
облачных хранилищ одновременно.

Основной сценарий использования — **десктоп-приложение** на вашей
собственной машине: скачал, запустил, появилась иконка в системном трее,
браузер открылся сам. Работа в безголовом режиме как сервис (на
сервере/в контейнере/под systemd, встроенный в другой backend, который
просто дёргает его REST API) — это **дополнительная, опциональная**
возможность того же бинарника, без отдельной сборки. Режим автоопределяется
из окружения (есть графическая сессия или нет), либо задаётся явно флагом
`-gui`/`-gui=false`.

## Зачем

Загрузка одного и того же файла (или пачки файлов) в несколько облачных
хранилищ обычно означает несколько разных инструментов — у каждого свой флоу
авторизации, своя логика повторных попыток и никакой общей истории того, что
и куда реально загрузилось. Cloud Uploader — единое приложение, которое:

- загружает в несколько хранилищ **параллельно** (по одной очереди на каждое
  подключённое хранилище, все очереди работают одновременно; внутри одного
  хранилища файлы грузятся строго последовательно, один за раз);
- ведёт **локальную проверяемую историю** каждой загрузки — включая
  чек-сумму — чтобы позже можно было убедиться, что файл всё ещё существует
  и не изменился на удалённом хранилище, даже если кто-то вручную удалил или
  заменил его там;
- хранит учётные данные в **системном хранилище паролей ОС** (Windows
  Credential Manager / macOS Keychain / Linux Secret Service), никогда — в
  открытом текстовом конфиге;
- полностью **портативен**: всё остальное состояние (подключения, история,
  настройки, правила слежения, логи) живёт в одной папке `data/` рядом с
  самим бинарником, никогда — в стандартном для ОС месте на пользователя;
  перенеси или скопируй всю эту папку куда угодно — продолжит работать, а
  два разных инстанса на одной машине никогда случайно не разделят
  состояние;
- умеет **следить за локальным файлом или папкой** и автоматически ставить
  изменения в очередь (`internal/watch`, `GET`/`POST /api/v1/watches`) — та
  же очередь, тот же прогресс и та же история, что и у ручной загрузки;
- проверяет наличие новой версии **только по вашему запросу** (Settings →
  «Check for updates») — cloudup иначе никогда сам не обращается в сеть по
  собственной инициативе, и здесь не исключение;
- спроектировано так, чтобы добавление **нового хранилища** сводилось к
  написанию одного нового пакета, без изменений в ядре;
- для больших файлов автоматически переключается на **порционную
  загрузку** хранилища (multipart у S3, upload-сессии у Dropbox), при этом
  прогресс остаётся непрерывным, а чек-сумма — одна на весь файл;
- для S3 и Backblaze B2 умеет дополнительно грузить части одного большого
  файла по нескольким соединениям одновременно (**multi-thread-streams**,
  как одноимённый флаг у rclone) — настраивается в Settings, включается
  выше настраиваемого порога размера, а не всегда;
- документирует весь API как **OpenAPI-спеку** ([`openapi.yaml`](openapi.yaml)),
  чтобы любой мог написать свой фронтенд вместо использования встроенного.

## Поддерживаемые хранилища

| Провайдер | Примечание |
|---|---|
| **Google Drive** | OAuth2 (Drive API v3) |
| **Amazon S3** и S3-совместимые | MinIO, Backblaze B2, Wasabi, Yandex Object Storage — через настраиваемый endpoint |
| **WebDAV** | Nextcloud, ownCloud, box.com и любой стандартный WebDAV-сервер |
| **Dropbox** | OAuth2 (Dropbox API v2) |
| **Backblaze B2** | нативный b2api v2 — серверный SHA1 делает проверку чек-суммы дешёвым запросом метаданных |
| **Yandex.Disk** | нативный REST API v1, OAuth2 — серверный MD5 делает проверку чек-суммы дешёвым запросом метаданных, в отличие от его generic WebDAV-интерфейса |
| **OneDrive / SharePoint** | OAuth2 (Microsoft Graph API v1.0) — опциональный `driveId` нацеливает на конкретную SharePoint document library вместо личного диска |
| **FTP** | RFC 959, с опциональным explicit TLS (FTPS) для серверов, которым нужен зашифрованный канал |
| **SFTP** | SSH File Transfer Protocol — пока только аутентификация по паролю (см. "Известные пробелы" ниже) |

Добавление ещё одного хранилища означает реализацию одного интерфейса
(`provider.Provider`, см. [CONTRIBUTING.ru.md](CONTRIBUTING.ru.md)) в
новом пакете — код очереди, истории и REST API не меняется.

## Статус проекта

**Всё перечисленное ниже реализовано и протестировано.**

- ✅ **Ядро** — интерфейсы провайдеров, девять хранилищ, секреты, конфиг,
  история в SQLite, очередь загрузки с retry/паузой/отменой, слежение за
  локальными папками.
- ✅ **REST API** (`internal/httpapi`, `cmd/server`) — подключения,
  загрузки, очередь (прогресс через поллинг), история (с пагинацией),
  настройки, слежение за папками, общий OAuth-флоу (Google Drive, Dropbox,
  Yandex.Disk, OneDrive) — задокументировано в [`openapi.yaml`](openapi.yaml).
- ✅ **Фронтенд** (`frontend/`, Vue 3 + Vite) — эталонный UI, покрывающий
  все эндпоинты. По умолчанию отдаётся самим `cmd/server` (один процесс,
  один порт, браузер открывается автоматически), либо запускается отдельно
  против любого cloudup-сервера.
- ✅ **Десктопный и серверный режимы из одного бинарника** — иконка в трее
  и автооткрытие браузера при наличии графической сессии, обычный
  headless-сервис в остальных случаях (`-gui`, автоопределение).

**Известные пробелы**:
- Методы `internal/providers/googledrive` (upload/download/list/delete) не
  покрыты интеграционными тестами — не нашлось качественного in-memory
  фейка под wire-протокол Drive v3, в отличие от WebDAV/S3. Перед реальным
  использованием — ручная проверка на живом Google-аккаунте.
- Живой OAuth-флоу и поведение Graph API у `internal/providers/onedrive`
  (автовивификация папок, границы размера чанка, формат редиректа
  скачивания) выведены из официальной документации, но не подтверждены
  живым запросом к реальному Azure AD App Registration.
- `internal/providers/sftp` не проверяет ключ хоста (нет хранилища вроде
  known_hosts или UI для подтверждения отпечатка) и умеет только
  аутентификацию по паролю — вход по ключу пока не реализован.
- Осталась пара проверок, которые можно сделать только вручную: реальные
  клики по иконке в трее, сборка с `-H=windowsgui`, автоопределение
  headless-режима по-настоящему без графической сессии.

## Быстрый старт

### Скачать готовую сборку

Каждый [GitHub Release](https://github.com/Charmer/cloudup/releases)
содержит zip-архив на каждую платформу (Windows amd64, macOS на Apple
Silicon, Linux amd64/arm64 — сборки под Intel Mac нет), собранный
[`.github/workflows/release.yml`](.github/workflows/release.yml) из
запушенного тега `vX.Y.Z`. В каждом архиве уже лежат собранный фронтенд и
`openapi.yaml` рядом с бинарником, в раскладке, при которой дефолты сразу
работают — распакуй и запусти бинарник прямо из распакованной папки, без
флагов. В Windows-архиве два бинарника: `cloudup-server.exe` (собран с
`-H=windowsgui` — без консольного окна, то, что нужно большинству) и
`cloudup-server-console.exe` (обычная сборка — если хочется смотреть лог
живьём в терминале, а не через `server.log`).

### Собрать из исходников

Требуется Go 1.22+ и Node 18+ (для фронтенда).

```bash
git clone https://github.com/<your-username>/cloudup.git
cd cloudup
go build ./...
go test ./...
```

### Запуск приложения

Собери фронтенд один раз, затем запусти сервер — он сам отдаёт фронтенд,
открывает браузер и по умолчанию работает как **приложение в системном
трее**, а не как обычный процесс на переднем плане: появляется иконка в
трее, левый клик по ней открывает браузер заново, если вкладку закрыли,
правый клик показывает пункт «Exit», который полностью завершает
приложение. Закрытие вкладки браузера **не** останавливает сервер — реально
работает именно иконка в трее.

```bash
cd frontend && npm install && npm run build && cd ..
go run ./cmd/server
```

Заметка для локальной разработки: `go run` компилирует временный бинарник
во временную папку, которая удаляется сразу после завершения процесса, а
состояние cloudup живёт в папке `data/` рядом с тем бинарником, который
реально запущен (см. [CONTRIBUTING.ru.md](CONTRIBUTING.ru.md)) — поэтому состояние,
созданное через `go run`, не переживает следующий `go run`. Для всего, что
должно сохраняться между перезапусками, собери настоящий бинарник:
`go build -o cloudup-server ./cmd/server && ./cloudup-server`.

Сервер стартует на `http://127.0.0.1:3000`, открывает эту страницу в
браузере по умолчанию — уже авторизованную (API-токен вшивается прямо в
страницу, копировать вручную не нужно), и пишет лог в `data/server.log`
рядом с бинарником вместо консоли (её обычно и не видно — см. заметку про
Windows-сборку ниже).

Чтобы кнопка «Check for updates» на странице Settings показывала реальную
версию вместо `dev`, собирай с вшитым тегом версии:

```bash
go build -ldflags "-X main.version=$(git describe --tags)" -o cloudup-server ./cmd/server
```

`-update-repo owner/repo` (по умолчанию `Charmer/cloudup`) указывает, в
каком GitHub-репозитории проверять — пригодится для форка. Это
единственный вызов, который cloudup делает по собственной инициативе;
без клика он никогда не происходит.

**На Windows** `go run`/обычный `go build` всё равно покажет консольное
окно позади иконки трея — это управляется PE-подсистемой exe-файла, не
поведением приложения во время выполнения. Чтобы получить настоящий запуск
без консоли, собирай так:

```bash
go build -ldflags="-H=windowsgui" -o cloudup-server.exe ./cmd/server
```

**Если вообще не запускается** — чаще всего потому, что распакован в
папку без прав на запись (например, `Program Files`: cloudup нужно
создать `data/`-папку рядом со своим бинарником, см.
[CONTRIBUTING.ru.md](CONTRIBUTING.ru.md)) — а окно консольной сборки
при двойном клике закрывается раньше, чем видна ошибка. Два способа её
увидеть: запустить `.exe` из уже открытого терминала вместо двойного
клика, либо посмотреть `%TEMP%\cloudup-startup-error.log` — туда любая
фатальная ошибка при старте пишется всегда, консоль есть или нет
(включая сборку с `-H=windowsgui`, у которой консоли для вывода нет
вообще). **Не обходите это запуском от администратора** — вместо этого
перенесите папку: Windows не показывает иконку в трее для elevated-процесса
в обычной desktop-сессии, и вы получите запущенный процесс без иконки и
без способа закрыть его кроме как через Диспетчер задач, тоже запущенный
от администратора.

GUI-режим (трей + автооткрытие браузера) **автоопределяется** из
окружения, если флаг `-gui` не передан явно: на голой Linux-машине, в
контейнере или под systemd (нет `DISPLAY`/`WAYLAND_DISPLAY`) сервер сам
переходит в обычный процесс на переднем плане с логом в консоль — один и
тот же бинарник работает и как десктоп-приложение, и как безголовый
сервис/backend-деплой, без двух отдельных сборок. Передай `-gui=false`
явно, если хочешь быть уверен независимо от окружения (например, для
Windows-службы, где эвристика автоопределения слабее — см.
`cmd/server/gui_detect_windows.go`):

```bash
go run ./cmd/server -gui=false
```

Чтобы разрабатывать фронтенд с hot reload, запусти его отдельным процессом
против уже работающего сервера — см. [`frontend/src`](frontend/src) и
комментарий в `api.js` о том, как он находит сервер (страница Settings
позволяет указать другой origin, например пока работает `npm run dev`):

```bash
# только API, без фронтенда, обычная консоль, CORS разрешён для origin Vite
go run ./cmd/server -static "" -gui=false -cors-origin http://localhost:5173
cd frontend && npm run dev   # отдельный dev-сервер с hot reload
```

`-cors-origin` нужен **только** здесь. CORS — механизм, существующий
исключительно внутри браузера, и по умолчанию он выключен: при обычном
запуске на одном порту страница и API имеют один origin, поэтому браузер
вообще не начинает CORS-проверку, а не-браузерному клиенту (`curl`, другой
backend, дёргающий этот сервис) эти заголовки не нужны и не читаются.
Важно: CORS никогда не был защитой этого API — чужая страница и без него
может *отправить* запрос на loopback-порт, same-origin policy запрещает
только *прочитать ответ*. Защищает bearer-токен.

### Опционально: безголовый запуск через Docker

Всё описанное выше — основной сценарий: cloudup как десктоп-приложение на
вашей собственной машине. Безголовый запуск как сервер — дополнительная,
опциональная возможность, и [`Dockerfile`](Dockerfile) /
[`docker-compose.yml`](docker-compose.yml) приведены исключительно как
**рабочий пример** такого сценария — отправная точка для адаптации под
себя, а не поддерживаемая цель развёртывания.

```bash
docker compose up -d --build
```

Это собирает образ безголового сервера (multi-stage: `frontend/` через Node,
Go-бинарник, затем тонкий рантайм-слой). **Реальная оговорка**:
`internal/secrets` требует системное хранилище паролей ОС (Windows
Credential Manager / macOS Keychain / Linux Secret Service — см.
[CONTRIBUTING.ru.md](CONTRIBUTING.ru.md)), которого у голого контейнера нет, а
секретное поле нужно каждому провайдеру — без хранилища паролей ни одно
подключение создать не получится вообще.
[`docker/entrypoint.sh`](docker/entrypoint.sh) обходит это, запуская внутри
контейнера приватную D-Bus-сессию и автоматически разблокированный
`gnome-keyring`. Эта настройка **не проверена реальной сборкой на живом
Docker-демоне в этой сессии** — воспринимай как отправную точку, а не
гарантию. Контейнер также слушает `0.0.0.0` вместо обычного дефолта
`127.0.0.1` — иначе Docker не смог бы прокинуть порт наружу до процесса,
слушающего только loopback контейнера; от этого API по-прежнему защищает
bearer-токен (та же логика, что и в заметке про CORS выше), поэтому в
`docker-compose.yml` обязательно замени `CLOUDUP_API_TOKEN` на настоящее
случайное значение, а не оставляй плейсхолдер.

### Авторизация Google Drive, Dropbox, Yandex.Disk и OneDrive

Эти четыре требуют одноразовый интерактивный OAuth-шаг, прежде чем
подключением можно пользоваться (почему — см.
[CONTRIBUTING.ru.md](CONTRIBUTING.ru.md)). Client ID/Secret для OAuth — настройка на
уровне всего приложения, **одна на тип провайдера**, а не на подключение —
получаемая один раз через приложение, зарегистрированное у каждого
провайдера.

**Единственное, что нужно каждому провайдеру**: зарегистрировать
собственный колбэк-эндпоинт cloudup, `<базовый URL вашего cloudup>/api/v1/oauth/callback`,
как **точный** redirect URI приложения — например
`http://127.0.0.1:3000/api/v1/oauth/callback` для обычного локального
запуска, либо ваш настоящий публичный URL (за reverse proxy) для
удалённого развёртывания. Это фиксированный, заранее известный URL —
cloudup строит его сам из того адреса, по которому ваш собственный браузер
прямо сейчас обращается к API, так что он автоматически верный и для
десктопного запуска, и для удалённого сервера, и регистрировать его нужно
только один раз на провайдера.

- **[Google Cloud Console](https://console.cloud.google.com/apis/credentials)**:
  сначала включи Drive API, затем создай OAuth-клиент типа **«Web
  application»** (не «Desktop app» — этот тип для другого флоу, который
  здесь больше не используется) и добавь redirect URI в «Authorized
  redirect URIs». Запрашиваемый scope: `drive.file` — доступ ограничен
  файлами, которые создаёт сам cloudup, а не ко всему Диску, так что не
  жди, что через него будут видны уже существующие файлы. Пока приложение
  в статусе «Testing» (по умолчанию), авторизовать его смогут только
  Google-аккаунты, явно добавленные как test users — частый сюрприз при
  первом запуске.
- **[Dropbox App Console](https://www.dropbox.com/developers/apps)**:
  создай приложение с **«Scoped access»**, access type **«Full Dropbox»**
  (не «App folder» — `rootPath` это путь, который выбираешь сам, а не
  изолированная папка, которую подбирает Dropbox). Добавь redirect URI в
  Settings. На вкладке **Permissions** явно отметь: `account_info.read`,
  `files.content.write`, `files.content.read`, `files.metadata.read`,
  `files.metadata.write` — Dropbox требует отметить каждый из них там,
  даже если приложение уже запрашивает их в самом запросе авторизации.
- **[oauth.yandex.ru/client/new](https://oauth.yandex.ru/client/new)**:
  отметь платформу **«Веб-сервисы»** — именно это открывает поле Redirect
  URI вообще; у остальных платформ нет сравнимого флоу с редиректом через
  браузер. Введи redirect URI (в консоли есть помощник «подставить URL для
  разработки» для локального адреса). Отметь права:
  `cloud_api:disk.write`, `cloud_api:disk.read`, `cloud_api:disk.info`.
- **[Azure App Registration](https://portal.azure.com/#view/Microsoft_AAD_RegisteredApps/ApplicationsListBlade)**:
  добавь redirect URI под платформой **«Web»** (не «Mobile and desktop
  applications», хотя cloudup именно такое приложение — «Web» это то, что
  принимает client secret и заранее зарегистрированный точный URI, а флоу
  теперь работает именно так). Нюанс, найденный на практике: ввести
  `http://127.0.0.1` через обычный интерфейс портала нельзя — схема
  `http` для него отклоняется; используй
  `http://localhost:<port>/api/v1/oauth/callback` для локального запуска
  (Azure считает `localhost`, в отличие от `127.0.0.1`, «родным» для
  портала) либо настоящий `https://`-URL для развёртывания. Добавь
  delegated-права `Files.ReadWrite`, `User.Read`, `offline_access`.

Во фронтенде это блок OAuth-клиентов на странице Settings, затем кнопка
«Authorize» рядом с подключением. Напрямую через API:

```bash
TOKEN=<API-токен>

# Один раз на тип провайдера
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"clientId":"...","clientSecret":"..."}' \
  http://127.0.0.1:3000/api/v1/provider-types/googledrive/oauth-credentials

# На каждое подключение: запустить флоу, открыть полученный authUrl, затем поллить
curl -X POST -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:3000/api/v1/connections/<id>/oauth/authorize
curl -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:3000/api/v1/connections/<id>/oauth/authorize
```

Каким типам провайдеров это нужно, сообщает `GET /api/v1/provider-types`
полем `requiresOAuth` — список нигде не захардкожен.

### Как добавить язык интерфейса

Переводы отдаёт бэкенд, а не сборка фронтенда: `GET /api/v1/languages`
перечисляет установленные языки, `GET /api/v1/languages/{code}` отдаёт
строки конкретного. Английский и русский вшиты в бинарник.

Чтобы добавить язык, положи один JSON-файл рядом с исполняемым файлом и
перезапусти — **без пересборки** ни Go, ни фронтенда:

```
cloudup-server
languages/
  de.json      # {"__name__": "Deutsch", "nav.queue": "Warteschlange", ...}
```

Имя файла — код языка; зарезервированный ключ `__name__` — самоназвание
языка, именно оно попадает в переключатель на странице настроек. Файл с
именем встроенного языка (`en.json`, `ru.json`) переопределяет только те
ключи, которые в нём есть, — можно поправить одну строку, не копируя весь
каталог. Пропущенные ключи дополняются английским при загрузке, поэтому
неполный перевод безопасен. Флаг `-languages <dir>` указывает другую папку —
пригодится на сервере, где каталог с бинарником только для чтения. Полный
список ключей — в
[`internal/i18n/languages/en.json`](internal/i18n/languages/en.json).

## Архитектура и контрибьютинг

Цель дизайна: **добавление нового хранилища никогда не должно требовать
изменений в ядре.** Как это устроено на практике — модель интерфейсов
провайдера, самостоятельная регистрация, OAuth, структура пакетов — плюс
чеклист перед pull request теперь живут в
[`CONTRIBUTING.ru.md`](CONTRIBUTING.ru.md), раз это нужно именно тем, кто
собирается контрибьютить. Для визуального разбора — путь загрузки, модель
полос в очереди, правило зависимостей в виде схем — открой
[`docs/architecture.html`](docs/architecture.html) в браузере.

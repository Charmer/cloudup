# Контрибьютинг в Cloud Uploader

*[Read in English](CONTRIBUTING.md)*

Контрибьюшены приветствуются. Этот документ описывает архитектуру,
которая понадобится при внесении изменений, и чеклист перед открытием
pull request.

## Как предложить изменение

У вас нет прав на запись в этот репозиторий — их нет ни у кого, кроме
мейнтейнера, осознанно. Форкните репозиторий, создайте ветку, закоммитьте
и откройте pull request обратно в `master`;
[`.github/workflows/ci.yml`](.github/workflows/ci.yml) прогоняет
`gofmt`/`go vet`/`go test`/сборку фронтенда на каждый PR — вы увидите
зелёное/красное ещё до того, как кто-то откроет диф руками.

```bash
gofmt -l .
go vet ./...
go test ./... -count=1
cd frontend && npm run build
```

Прогоните все четыре команды локально перед пушем — тот же гейт, что и в
CI, просто быстрее узнать результат.

## Архитектура

> Визуальный разбор — путь загрузки, модель полос в очереди и правило
> зависимостей в виде схем — в
> [`docs/architecture.html`](docs/architecture.html): откройте файл в
> браузере. Это один самодостаточный файл; текст ниже покрывает то же
> самое прозой.

Цель дизайна: **добавление нового хранилища никогда не должно требовать
изменений в ядре.** Несколько принципов обеспечивают это на практике.

### Композиция маленьких интерфейсов, а не один большой

Каждый провайдер реализует один маленький обязательный интерфейс:

```go
type Provider interface {
    Type() string
    DisplayName() string
    TestConnection(ctx context.Context) error
    Upload(ctx context.Context, task UploadTask) (UploadResult, error)
    Download(ctx context.Context, task DownloadTask) error
    List(ctx context.Context, remotePath string) ([]RemoteEntry, error)
    Delete(ctx context.Context, remotePath string) error
}
```

Всё, что умеют не все хранилища — multipart-загрузка, параллельная загрузка
частей одного файла по нескольким соединениям, проверка чек-суммы, проверка
существования файла, отчёт о квоте, описание собственной формы
конфигурации — отдельный опциональный интерфейс
(`internal/provider/features.go`). Ядро определяет поддержку через type
assertion (`p.(provider.ChecksumVerifier)`) и корректно откатывается, если
провайдер его не реализует. Ни один провайдер не обязан реализовывать
заглушки для того, что не умеет: API `upload_session` у Dropbox требует,
чтобы смещение каждого чанка точно совпадало с тем, что сервер уже принял,
поэтому он просто никогда не реализует `ParallelMultipartUploader` — это
ограничение протокола, а не недоделанная функция.

### Провайдеры регистрируют себя сами

Каждый пакет провайдера регистрирует себя в собственном `init()` — до трёх
отдельных вызовов, по одному на каждую заботу ядра, ни один из которых не
требует, чтобы ядро импортировало пакет провайдера:

```go
// internal/providers/s3/s3.go
func init() {
    registry.Register(Type, New)                 // фабрика Provider
    registry.RegisterSchema(Type, ConfigFields)   // форма подключения (см. ниже)
    // registry.RegisterOAuth(Type, oauthFlow())  // только если нужна интерактивная авторизация
}
```

Ядро (`internal/registry`) никогда не импортирует конкретный пакет
провайдера и не содержит `switch` по типам хранилищ. Новое хранилище — это
новый пакет плюс анонимный импорт (`import _ "cloudup/internal/providers/<name>"`)
в `cmd/server/main.go` — больше ничего менять не нужно.

### Форма подключения провайдера — это данные, а не код фронтенда

`ConfigFields() []provider.FieldSpec` каждого провайдера (интерфейс
`provider.ConfigSchema`) описывает собственную форму подключения —
`{Key, Label, Type (text/password/select), Required, Options}` на поле,
например у WebDAV (`internal/providers/webdav/webdav.go`):

```go
func (p *Provider) ConfigFields() []provider.FieldSpec {
    return []provider.FieldSpec{
        {Key: "url", Label: "Server URL", Type: provider.FieldText, Required: true},
        {Key: secretUsername, Label: "Username", Type: provider.FieldPassword, Required: true},
        {Key: secretPassword, Label: "Password", Type: provider.FieldPassword, Required: true},
    }
}
```

`GET /api/v1/provider-types/{type}/schema` (`internal/httpapi/connections.go`)
просто транслирует это напрямую из `registry.Schema(type)` в JSON —
REST-слой никогда не видит конкретный список полей, только то, что
объявил провайдер. `ConnectionsView.vue` рендерит форму, перебирая этот
массив (`v-for="f in schema"`, решая тип инпута по `f.Type`) — ноль
кода под конкретного провайдера во фронтенде. При отправке на клиенте
происходит тот же общий разбор: всё с `Type === 'password'` уходит в
`secrets{}` тела запроса, остальное — в `fields{}`; бэкенд кладёт `fields`
в `config.json`, а `secrets` направляет в `internal/secrets` (OS
keychain) — ни один из них не знает заранее, какие ключи ожидать для
какого провайдера.

### Каждый провайдер сам решает свою стратегию проверки чек-суммы

WebDAV-серверы, большинство S3-совместимых хранилищ и Dropbox не отдают
надёжный хэш содержимого, поэтому эти провайдеры сами считают SHA-256 во
время стриминга загрузки и проверяют позже через повторную закачку и
пересчёт. Google Drive, Backblaze B2 и Yandex.Disk, наоборот, надёжно
возвращают собственный хэш в метаданных файла (`md5Checksum`, SHA1 и `md5`
соответственно), поэтому их `VerifyChecksum` — это дешёвый metadata-запрос.
Ядро не знает и не заботится о том, какую стратегию использует конкретный
провайдер — оно вызывает общий интерфейс `ChecksumVerifier`. Доверяем
только официально задокументированным полям метаданных — см. доккомментарий
пакета `internal/providers/yandexdisk` про случай, когда сторонний SDK
указывал лишнее поле, которого нет в официальном референсе API.

Пользовательская настройка «проверять чек-сумму после загрузки»
(`Settings.VerifyChecksumAfterUpload`) — это обычный `map[string]bool` по
типу провайдера: бэкенд хранит и применяет её, вообще не зная, какие типы
дешёвые, а какие дорогие для проверки. Это разделение (то же самое
WebDAV/S3/Dropbox-передокачивание против Drive/B2/Yandex.Disk-metadata-
запроса, описанное выше) намеренно не попадает в Go-код, а живёт только как
небольшой захардкоженный массив `expensiveVerifyTypes` в `SettingsView.vue`,
показываемый рядом с каждым чекбоксом простой строкой-подсказкой. Держите
этот массив и этот раздел в синхроне при изменении стратегии проверки чек-
суммы у провайдера или добавлении нового — никакого маркера на уровне
реестра, который делал бы это автоматически, нет специально.

### OAuth2-авторизация живёт вне интерфейса провайдера

Подключение Google Drive/Dropbox/Yandex.Disk/OneDrive нельзя создать из
сохранённых конфига и секретов при первом использовании — сначала нужен
интерактивный шаг согласия (открыть браузер, пользователь одобряет
доступ, провайдер возвращает код через редирект). Это вынесено в
отдельную пару функций на провайдера (`AuthURL`/`Exchange`, см.
`internal/provider.OAuthFlow`, регистрируется тем же способом
самостоятельной регистрации, что и фабрика со схемой выше), вызываемую API
настройки подключения, а не встроено в `ConfigSchema` (которая описывает
только статичные поля формы, а не многошаговые интерактивные флоу).

Цель редиректа — `GET /api/v1/oauth/callback` на этом же REST API
сервере, а не отдельный временный процесс. Раньше использовался паттерн
RFC 8252 «loopback redirect», которым пользуются native/CLI-приложения
(временный HTTP-слушатель на `127.0.0.1:<случайный порт>`) — он ломался
двумя способами, как только у cloudup появились реальные сценарии
развёртывания: несколько провайдеров (подтверждено для Dropbox, вероятно
и для Yandex) требуют точный, заранее зарегистрированный redirect URI
вместе с портом — а случайный порт на каждую попытку никогда не совпадёт;
и случайный порт на `127.0.0.1` означает что-то только на той машине, где
он открыт — а это вообще не машина, на которой запущен `cloudup-server`,
если оператор управляет удалённым/headless-развёртыванием через браузер
на своём ноутбуке. Раз `cloudup-server` и так держит постоянный
HTTP-сервер — в отличие от типичного native-приложения — redirect URI
теперь ведёт обратно именно туда, построенный из того адреса, по
которому браузер и так уже обращается к API (`requestBaseURL` в
`internal/httpapi`, учитывающий `X-Forwarded-Proto`/`-Host` за reverse
proxy). Фиксированный для конкретного сервера и достижимый по построению.

### Прогресс — через поллинг, не push

`GET /api/v1/tasks` отдаёт текущее состояние всех задач загрузки; фронтенд
опрашивает его с интервалом вместо того, чтобы держать открытым
WebSocket/SSE-соединение. Проще на обеих сторонах и одинаково хорошо
подходит для REST API, рассчитанного на потребление не только встроенным
фронтендом.

### Всё локальное состояние — в одной портативной папке

`internal/appdir.Dir()` возвращает папку `data/` рядом с запущенным
исполняемым файлом — не стандартное для ОС место на пользователя
(`os.UserConfigDir()`, т.е. `%APPDATA%`/`~/Library/Application
Support`/`~/.config`), которое обычно использует десктоп-приложение.
`internal/config`, `internal/history`, `internal/settings` и
`internal/watch` резолвят свои файлы по умолчанию именно через неё, как и
лог-файл `cmd/server` в GUI-режиме. Смысл: скачанный релизный архив (или
собранная самостоятельно папка) — это **весь** инстанс целиком: перенеси,
скопируй, запусти два рядом — ничто из этого никогда не тронет общее,
управляемое ОС место вне этой папки. Единственное осознанное исключение —
`internal/secrets`, который по-прежнему использует настоящее системное
хранилище паролей ОС: в отличие от остальных хранилищ, весь смысл его
существования — положить креды куда-то **более** защищённое, чем обычный
файл в этой папке, а не куда-то более портативное.

Заметка для локальной разработки: `go run` компилирует временный бинарник
во временную папку, которая удаляется сразу после завершения процесса, а
значит состояние, созданное через `go run`, не переживает следующий
`go run` — для всего, что должно сохраняться между перезапусками, собери
настоящий бинарник (`go build -o cloudup-server ./cmd/server`).

### Структура пакетов

```
internal/
  provider/            Базовые интерфейсы (Provider + опциональные), SecretStore.
  appdir/              Резолвит единую папку "data/", где живут все файлы локального состояния.
  registry/             Регистрация и поиск фабрик провайдеров по строковому типу.
  providers/
    webdav/             WebDAV (Nextcloud, ownCloud, box.com и подобные).
    s3/                 AWS S3 + S3-совместимые хранилища, с MultipartUploader + ParallelMultipartUploader.
    googledrive/        Google Drive API v3, OAuth2.
    dropbox/            Dropbox API v2, OAuth2 (app-wide client credentials).
    b2/                 Нативный API Backblaze B2, потоковая загрузка с трейлинг-SHA1, ParallelMultipartUploader.
    yandexdisk/         Yandex.Disk REST API v1, OAuth2, нативная MD5-чек-сумма из метаданных.
    onedrive/           Microsoft Graph API v1.0, OAuth2, нативная quickXorHash-чек-сумма из метаданных.
  streamio/             Общие обёртки io.Reader/io.Writer для отчёта о прогрессе.
  secrets/              Реализация SecretStore поверх системного хранилища паролей ОС.
  config/               JSON-хранилище конфигурации подключений (только несекретные поля).
  history/               Журнал загрузок в SQLite + последующая перепроверка.
  queue/                 Планировщик загрузок: параллельно между хранилищами, последовательно внутри одного, retry/pause/cancel.
  watch/                 Следит за локальным файлом/папкой (fsnotify) и ставит изменения в ту же queue.Manager.
  settings/              JSON-хранилище настроек приложения (конкурентность, verify-after-upload, ...).
  httpapi/                REST API поверх всего вышеперечисленного — контракт см. в openapi.yaml.
  debuglog/              Опциональное (CLOUDUP_DEBUG=1) логирование HTTP-трафика для диагностики проблем с провайдерами.
  oauthflow/             Общая OAuth2-механика (AuthURL/Exchange) для провайдеров с интерактивной авторизацией.
  updatecheck/           Проверка релиза на GitHub по запросу для кнопки "Check for updates" — никогда автоматически.
  i18n/                   Каталоги переводов UI: встроенные по умолчанию + внешние JSON-файлы.
cmd/
  server/                 REST API + (по умолчанию) собранный фронтенд, один процесс/порт.
frontend/                Эталонный фронтенд на Vue 3 + Vite, работает с openapi.yaml по HTTP.
```

### Модель параллелизма

Одна очередь на каждое подключённое хранилище; очереди разных хранилищ
работают полностью параллельно. Внутри одного хранилища загрузки стартуют
в порядке FIFO, до настраиваемого лимита параллелизма (Settings → «Max
concurrent uploads per connection», по умолчанию 1 — строго
последовательно, что лучше соответствует тому, как ведёт себя большинство
API под одним запросом на аккаунт за раз, чем под интенсивным внутренним
параллелизмом).

## Чеклист перед pull request

- Тесты лежат рядом с кодом, который они тестируют (`<file>_test.go` в том
  же пакете) — стандартная конвенция Go, а не отдельное дерево `tests/`.
- `gofmt -l .`, `go vet ./...` и `go test ./... -count=1` (в идеале
  `-count=3` — ловит утечки глобального состояния между прогонами,
  которые одиночный `-count=1` может не заметить) все проходят. CI
  прогоняет те же проверки на вашем PR.
- При добавлении нового провайдера хранилища реализуй `provider.Provider`
  плюс те опциональные интерфейсы, которые имеют смысл для этого
  хранилища, и зарегистрируй его через `init()` — самый простой пример для
  копирования — `internal/providers/webdav`.
- Секреты не должны попадать в `internal/config` — всё чувствительное
  живёт в `internal/secrets`.
- Изменение публичного эндпоинта `internal/httpapi` должно сопровождаться
  правкой `openapi.yaml` в том же изменении.
